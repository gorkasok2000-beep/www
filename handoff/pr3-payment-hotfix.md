# PR-3: Серверный hotfix платежей — статусы после отправки, фильтр по userOpHash, атомарные захваты (B1, H3, H4, H5, M5)

**Ветка:** `pr3-payment-hotfix` → `claude/synth-wallet-prototype-ox1cd0`
**Коммит:** `e65bd5a`
**Файлы:** `apps/web/src/lib/payments.ts` (+189/−74), `apps/web/src/lib/chain/relayer.ts` (+38/−12), `apps/web/src/lib/invoices.ts` (+2), `apps/web/prisma/schema.prisma` (+4/−2, только комментарии)

## Что закрывает

### B1 (blocker) — прошедший в сети платёж мог быть помечен FAILED → двойная трата

`execute` в `payments.ts` разделён на две фазы с разной ценой ошибки:

- **До отправки** (симуляция, сборка, подпись): сеть платёж не видела — любая ошибка
  честно переводит его в `FAILED` с причиной, захваченный счёт возвращается в `OPEN`;
- **После отправки**: ошибка статуса **не меняет**. Операция могла уйти в сеть, и ложный
  `FAILED` спровоцировал бы агента заплатить второй раз. Платёж остаётся `SUBMITTED`,
  правду о нём скажет сверка `reconcilePayments`.

`syncTransactionLogs()` вынесен из критичного `try` и работает best-effort **после**
`finalize`: сбой индексатора больше не может перезаписать `CONFIRMED` на `FAILED`.

### H3 (high) — сервер не различал события своей и чужих UserOperation

`readUserOperationOutcome(txHash, userOpHash)` в `relayer.ts`:

- декодирует события только с `args.userOpHash === userOpHash` — чужая failed op в том
  же бандле не делает наш платёж `FAILED`;
- проверяет `receipt.status`: откатившаяся целиком транзакция бандлера → `null`;
- возвращает `null` («неизвестно»), если нашей операции в чеке нет. Раньше отсутствие
  событий читалось как `success: true` — полный revert бандла выглядел успешным платежом.

Сигнатура изменилась (добавлен `userOpHash`, возврат `| null`); обновлены все
вызывающие: `payments.ts`, `findUserOperationByHash`, `assertUserOperationSucceeded`,
`sendAgentUserOperation`.

### H4 (high) — блокировка «один платёж за раз» не атомарна

Проверка in-flight и `payment.create` теперь идут в одной `db.$transaction`, которая
первым делом выполняет формальный `UPDATE` строки агента: SQLite допускает лишь одного
писателя, и writer-lock сериализует параллельные платежи одного агента. Два конкурентных
запроса больше не проходят проверку одновременно и не берут один нонс.

### H5 (high) — двойная оплата одного счёта

- Оплата счёта атомарно захватывает его `OPEN → PAYING` (`updateMany` с условием на
  статус) в той же транзакции, до исполнения. Второй претендент — хоть этот же агент,
  хоть другой — получает `count = 0` и 409;
- `finalize` трогает счёт, только если он всё ещё `PAYING` (захвачен этим платежом):
  успех → `PAID`, подтверждённый сетью отказ → обратно в `OPEN`;
- `requirePayableInvoice` в `invoices.ts` отвечает 409 на статус `PAYING`.

### M5 (medium) — «зомби»-платежи CREATED навсегда блокировали агента

`CREATED` старше 5 минут (`CREATED_TTL_MS`) — след процесса, упавшего между созданием
записи и отправкой: сеть его не видела и не увидит. Такой платёж гасится в `FAILED`
(`updateMany` с условием `status: "CREATED"` — живой, уже ушедший в `SUBMITTED`, не
задевается) и освобождает захваченный счёт. Гашение происходит двумя путями: при ретрае
со старым ключом идемпотентности (возвращается погашенный платёж, а не «живой» created)
и при входе нового платежа (зомби чистятся до проверки in-flight — 409 больше не
зависает навсегда).

## Совместимость

- Публичный HTTP API не меняется: те же поля, те же коды ответов. Идемпотентность по
  `requestHash` сохранена.
- Prisma-схема: статусы — строки (SQLite), миграция не нужна; изменены только
  документирующие комментарии (`PAYING`, TTL для CREATED).
- Контракты не тронуты.

## Проверки

- `tsc --noEmit` по `apps/web` — чисто (прогон в этой среде, TypeScript 5).
- `.diff` проверен применением к чистому снапшоту репозитория (`git apply --check` — OK).
- ⚠️ Юнит-/сценарных тестов у web-приложения в репозитории нет, живой прогон на anvil
  здесь невозможен (`forge`/`anvil` отсутствуют). Перед merge рекомендуется ручной
  сценарий: параллельные платежи одним агентом, падение RPC после отправки, два агента
  на один счёт, зомби CREATED старше 5 минут.
